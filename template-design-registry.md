### Header component changelog (applies to all pages in this template)
The header went through two corrective revisions after initial launch — noted here so future templates don't repeat the same mistakes:
1. **Grid → Flex:** original header used `grid-cols-3` (three *equal* thirds: left-nav / centered-logo / right-nav+controls). Equal-thirds tracks don't grow to fit content — the right column (nav + icons + CTA) needed far more than 1/3 of the header width at realistic desktop sizes, overflowing and visually overlapping the centered logo. Replaced with a single flex row (logo `shrink-0` + nav `flex-1` + controls `shrink-0`) sized by actual content, not arbitrary fractions.
2. **Breakpoint lg → xl:** even the corrected flex layout was razor-thin at 1024px (`lg`) with 6 nav links; adding a 7th link (Home 2) would have overflowed again. Desktop nav/CTA now gate on `xl` (1280px) instead of `lg` (1024px) — tablet-landscape widths (1024–1279px) now correctly get the hamburger drawer instead of a cramped nav row. `DESKTOP_BREAKPOINT` in `main.js` was updated to match (1280).
Also fixed: the header's transparent-over-hero state (home page only) was replaced with a permanent semi-opaque glass background on every page, since dark nav text over a busy/dark hero photo was unreadable; and the mobile drawer's RTL "closed" position (`translateX(-100%)`) was removed entirely because it wasn't matched by an equal flip of the drawer's physical docking side (`right-0`), which pulled the panel partially into view the instant RTL was toggled — the drawer now always docks and slides from the right regardless of direction.

3. **Dark-mode icon-button hover contrast (found during the gallery.html redesign pass, fixed site-wide):** the header's icon buttons (`data-theme-toggle`, `data-dir-toggle`, `#drawer-open`) had `hover:text-raspberry-600` with no `dark:hover:text-caramel-400` counterpart — every other interactive element on the site already had this dark-mode override. Measured via the WCAG relative-luminance formula: raspberry-600 (#B4123F) against the choco-800 dark background is ≈2.32:1 contrast (fails the 3:1 minimum for UI components), while caramel-400 (#F7AE61) against the same background is ≈8.38:1 — confirming this was a real, measurable defect, not a stylistic nitpick. Also found and fixed: `#drawer-close`, every mobile drawer nav-link, and the drawer's own theme/direction pill buttons had **no hover state at all** (missing in both light and dark mode). Fixed by adding the missing `dark:hover:text-caramel-400` (+ a background-tint hover escalation) everywhere this pattern was missing, then propagating the corrected header/drawer block to all 11 pages. Two page-grouping subtleties to remember if this block is ever touched again: (a) icon buttons split into a "white group" (`bg-white/70` resting state — index, home-1, desserts, special-occasions, offers) and a "cream group" (`bg-cream-200/70` — about, contact, faq, menu, order, gallery), and substituting the wrong group's background silently miscolors that page's buttons; (b) the cream group's hover was originally just an opacity bump on its own resting color (`hover:bg-cream-200` over `bg-cream-200/70`, barely visible) — escalated to `hover:bg-cream-300` for a real, visible color shift.
4. **Active nav-link invisible in dark mode (stale class mismatch, `main.js` §5):** the active-state logic added `dark:text-caramel-400` but removed `dark:text-cream-200` — except the nav links' actual base class (desktop, mobile drawer, and dropdown-panel links alike, verified identical across all 11 pages) was `dark:text-cream-100`, not `-200`. `classList.remove()` silently no-ops on a class that isn't present, so the stale `dark:text-cream-100` was never cleared and sat alongside the newly-added `dark:text-caramel-400` on the same element — which of the two Tailwind utilities actually painted depended on arbitrary CSS source order rather than DOM class order, in practice leaving the "active" page's nav link visually indistinguishable from every inactive link in dark mode. (The sibling dropdown-trigger highlighting logic a few lines down, §5b, already removed the correct `dark:text-cream-100` — this bug was isolated to §5's own copy of the same pattern, evidently drifted out of sync at some point.) Fixed by correcting the removed class to `dark:text-cream-100`. Verified via jsdom with `.dark` forced on `<html>`: the active link (and, where the active page lives inside the Home dropdown, the dropdown trigger too) now carries `dark:text-caramel-400` with no leftover `dark:text-cream-100`/`text-choco-700`. Since the active-color and hover-color are the same value (`dark:text-caramel-400` both ways), the active tab now also correctly stays highlighted on hover, with no separate fix needed.
5. **Missing `color-scheme` CSS property (found while fixing the Menu category dropdown, applied site-wide):** the project toggles dark mode via a `.dark` class on `<html>`, but never told the browser which color scheme its own *native* form-control chrome should render in. Without `color-scheme: dark` set when `.dark` is active, a native `<select>` dropdown's open option-list popup can render in the browser/OS's default (often light) palette in some browsers regardless of the page's own dark styling — a real, well-documented gap, not a guess: every `<select>` on the site (Menu's sort dropdown, the new category dropdown, several on `order.html`) was exposed to it. Fixed with a two-line rule (`:root{color-scheme:light} .dark{color-scheme:dark}`) plus an explicit `.dark select option{background-color:#2E2016;color:#FFF8F0}` fallback for desktop browsers (Chrome/Firefox/Edge) that do let individual `<option>` elements carry their own colors — both additions are global, so every select on every page benefits, not just Menu's.
   - **Menu category dropdown (`#menu-category-select`), specifically:** added a `hover:border-raspberry-300 dark:hover:border-caramel-400` state (previously had no hover feedback at all — matching the sitewide gap that no form control anywhere had one); added `truncate` so a long selected label ("Corporate Events") can't visually overflow the pill shape on narrow widths; added `text-choco-700 dark:text-cream-100` explicitly (previously relied on inherited color, now stated so it can't drift); corrected the RTL icon-clearance padding from `rtl:pl-4` (too small — only 1rem, insufficient room for the chevron that moves to the left edge in RTL) to `rtl:pl-10` to match the same clearance the chevron gets on its LTR side; added `z-10` to the relative wrapper defensively (the native popup itself is unaffected by page z-index — browsers always render it above the document — but this guards the closed select box against being visually covered by a future absolutely-positioned neighbor). Verified via jsdom that the dropdown still correctly drives the grid, and that both the dropdown's own value and the sidebar button's `aria-pressed` stay in sync after a selection.

### gallery.html pagination redesign

The gallery grid was flattened and re-architected to support reliable pagination, and five new content sections were added below it so the page reads as more than "just a photo grid":

- **Grid:** removed the masonry treatment (`grid-flow-dense` + 7 scattered `row-span-2` tiles) in favor of uniform equal-size tiles at every breakpoint. Masonry's dense packing makes an exact "N rows per page" cut mathematically unreliable right at a page boundary; uniform tiles also directly satisfy the "consistent grid with equal card sizes" requirement rather than just being a pagination workaround.
- **Pagination (`main.js` §24):** shows exactly 3 rows per page, but — unlike `menu.html`'s fixed 9-per-page (see Menu redesign changelog below) — the gallery grid's column count changes per breakpoint (2/3/4 cols), so items-per-page is computed live as `3 × currentColumnCount`, with column count re-derived from the same `md`/`lg` `matchMedia` breakpoints the grid's own Tailwind classes use, recalculated on debounced resize. Desktop/tablet get numbered Prev/Next controls (jump to one page); mobile gets a cumulative "Load More" button. Changing the active category filter always resets to page 1; clicking a pagination control preserves the active category (each render pass re-derives the active category itself from `[data-filter][aria-pressed="true"]` rather than trusting any other module's `.hidden` state).
- **New content sections** (added between the grid and the CTA, each checked against every layout already used elsewhere on the site to guarantee no repeat): **Our Cake-Making Process** (a minimal icon-only ticker — deliberately not the numbered-circle/timeline/zig-zag treatments already used on Home, Home 2, Desserts, and About), **Custom Cake Design Service** (a two-column comparison card — order-as-shown vs. design-with-us — a layout not used anywhere else on the site), **Celebration Inspiration** (a pure-typography tag cloud, no cards/icons/images, linking directly into `menu.html`'s occasion anchors), and **Customer Stories** (one large spotlight testimonial, not a 3-card grid like Desserts/Special-Occasions). A "Gallery Highlights" section was considered but dropped as redundant with the main grid directly above it. A sixth section, "Featured Cake Collections" (an asymmetric bento image collage), was built at the same time but later removed at the user's request to keep the page leaner — its absence isn't a regression, just a deliberate trim.
- **CTA:** rebuilt with a diagonal clip-path split panel (left-aligned text + floating glass stat cards on a diagonally-clipped raspberry→caramel panel) instead of the centered-gradient-banner shape used on Home and elsewhere, so the page's closing section is visually distinct rather than a repeat.
- **No-JS-safe pagination default:** the 30→36-photo pool is hidden beyond position 12 with a static `hidden` class in the raw HTML itself (not just via JS), so the page shows a compact 12-photo grid even if JavaScript never runs — the pagination script's own `render()` call still recomputes the correct visible set for the real viewport on top of that safe default. This pattern was later reapplied to `menu.html` too (see below) once the same latent gap was recognized there.

### menu.html redesign — sidebar/dropdown category selector + compact browsing

The original Menu page had grown to 10 filter tabs (All + 9 occasions) wrapping across 2-3 lines above a fixed-12-per-page grid, plus an image-heavy "Event Category Cards" section that largely duplicated Special Occasions' own "Celebration Highlights" cards. Redesigned around a single principle — never show more than 9 products at once, regardless of which category is active:

- **Category selector:** the wrapping pill-tab row is gone. In its place: a **sticky left sidebar** (`xl:` 1280px and up — chosen instead of the more common `lg`/1024px so the 3-column grid never gets cramped alongside a fixed-width sidebar) with the same 10 categories as a vertical icon+label list, and a **compact native `<select>` dropdown** below `xl` (covering mobile, tablet, and small laptop widths in one control). Both drive the exact same underlying filter buttons/engine (`main.js` §9) — the dropdown is a thin adapter (`main.js` §25) that calls `.click()` on the matching hidden sidebar button rather than a second parallel filtering system, so there's only ever one source of truth for which category is active. The sidebar buttons themselves reuse the identical active/inactive utility classes the old pill tabs used, so the existing (unmodified) `activate()` function highlights them correctly with zero JS changes to section 9.
- **Category intro line** (`main.js` §25): a small icon + title + one-line description above the grid updates to match whichever category is active (sourced from a small hardcoded `CATEGORY_INFO` map), giving each category a lightweight "introduction" without a dozen hand-authored paragraph blocks.
- **Compact browsing depth:** `data-page-size` on `#menu-grid` dropped from 12 to 9. Since every individual category (after the two prior "fix incomplete rows" passes) already tops out at 9 items, this means **every category fits on a single page of exactly 6, 9, or 3 items — pagination only ever appears when "All" is selected**, which is precisely the "6 to 9 featured items per category, Load More for anything beyond that" behavior requested.
- **Removed:** the "Event Category Cards" section (6 large photo+text cards, redundant with Special Occasions' near-identical cards) and the bottom one-line "describe your custom cake" text (superseded by the sidebar's own persistent CTA card, see below).
- **New content, replacing the removed section, both low-image by design:** **Chef's Recommendations** (a 4-up strip of small circular-thumbnail chips — name, price, deep-link — not a photo grid) sits above the browsing area; **Build Your Own Combo** (3 icon-pair cards with no photos at all: Cake+Cupcakes, Party Pack, Office Celebration Bundle, each with a savings badge and an Order link) closes the page before the footer.
- **Custom-order info:** a persistent "Need Something Custom?" card is pinned at the bottom of the sidebar on `xl+` (always visible while browsing, not just at the end of the page); an equivalent card appears once, inline, on any narrower viewport where the sidebar is hidden.
- **No-JS-safe pagination default:** applied the same static-`hidden`-beyond-page-1 fix used on `gallery.html` — the 59 product cards beyond position 9 carry a static `hidden` class in the raw HTML, so the page never dumps all 59 at once even before JavaScript runs.
- Verified via a script that actually clicks every one of the 10 category buttons and counts real visible cards (not just reading the HTML): every category renders complete rows with no incomplete last row; the mobile `<select>` correctly drives the grid and stays in sync when a category is chosen from either control; the category intro line updates correctly from both the sidebar and the dropdown.

## Home Page 1 — `index.html` (existing entry, unchanged) vs. Home Page 2 — `home-1.html`

`home-1.html` ("Home 2" in nav) is an alternate homepage for the same brand — same tokens (color/type/header/footer/buttons/cards), deliberately different layout, hero composition, and section presentation from `index.html` per the master prompt's "Home 1 vs Home 2 must not share section layouts" rule.

- **Hero layout:** Split-screen (not full-bleed). Text column left (eyebrow badge, serif headline with one script word, paragraph, dual CTAs, inline trio of stat callouts separated by vertical dividers — no floating card). Image column right: single rounded-corner photo with a small overlapping "review quote" card anchored to its bottom-left corner (hidden below `sm` to avoid crowding).

### Lessons applied from Template 01's changelog
Two mistakes recorded in T1's header changelog were deliberately avoided here rather than re-learned: the centered-logo header used plain flex (`flex-1` siblings + `shrink-0` logo) from the very first draft instead of `grid-cols-3` equal-thirds, and desktop nav was gated at `xl` (1280px) from the start given a 6-link split nav needs at least as much room as T1's single-row 7-link version did.

### Content-accuracy note (image sourcing)
An initial pass populated photo placeholders with Unsplash `photo-<id>` URLs recalled from memory and verified only by HTTP 200 status — several turned out to depict unrelated subjects once rendered (a library interior captioned "Pre-K Classroom," a magnifying glass on a laptop captioned "Story Time," a street-photography shot in a gallery grid). HTTP 200 confirms a URL *resolves*, not that its *content* matches the caption. The fix: use `WebFetch` on Unsplash search-results pages (e.g. `unsplash.com/s/photos/preschool-classroom`) to extract real `images.unsplash.com/photo-…` URLs paired with their actual alt-text descriptions, then verify those specific URLs return 200 — only then treat an image as content-verified. Every photo in this template was re-sourced this way. Apply this method from the start on future templates rather than as a corrective pass.
